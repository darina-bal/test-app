## Что сделано и что не успел

**Сделано**

- **Часть 1.** Экран «Матчи тура»: данные грузятся по `MATCHES_URL`; в карточке хозяева и гости, счёт (если он есть), дата и время начала в часовом поясе устройства, статус по-русски. Есть загрузка, ошибка с причиной и кнопкой «Повторить», два пустых состояния («в туре нет матчей» и «в этой категории нет матчей»). Фильтр «Все / Предстоящие / Завершённые». Кнопка «Обновить», pull-to-refresh и подпись «Обновлено N сек назад» на готовом `UpdatedAgo`.
- **Часть 2.** Звёздочка подключена к карточкам, обе жалобы воспроизведены и исправлены (см. ниже).
- **Необязательная задача: тест на логику фильтра** (`npm test`, 21 тест). Выбрано, потому что именно в фильтре легко потерять «неочевидные» статусы (`live`, `postponed`, неизвестный), а тест фиксирует принятое решение. Рядом лежат тесты разбора ответа сервера (счёт `0:0`, `startsAt: null`, битые записи): они про тот же класс проблем.

**Не успел / не проверено**

- Приложение проверялось в браузере (`npm run web`, Chrome). На телефоне в Expo Go оно не запускалось, поэтому pull-to-refresh и формат даты на Hermes не проверены.

## Решения

**Фильтр.**

| Вкладка | Статусы |
|---|---|
| Все | все, включая неизвестные |
| Предстоящие | `scheduled`, `live`, `postponed` |
| Завершённые | `finished` |

«Предстоящие» — всё, что ещё не закончилось: ждёт начала, идёт прямо сейчас или перенесено на потом. Так идущий и перенесённый матчи не пропадают из вкладок. «Завершённые» — только `finished`, то есть матчи с итоговым результатом. Статус, которого мы не знаем (например, отмена), не относится ни к одной из вкладок: не угадываем, а оставляем матч видимым во «Все» с подписью «Статус неизвестен».

**Неочевидные случаи в данных.**

- Счёт `0:0` (m2) — настоящий счёт, поэтому проверяются типы, а не «истинность» чисел; когда счёта нет (`score: null`), показывается «—».
- `startsAt: null` у перенесённого матча (m7) — «Дата уточняется», а не «Invalid Date» или 1970 год.
- Время приходит в UTC (`Z`) и форматируется без явного `timeZone`, то есть в поясе устройства. В Chrome проверено для Москвы, Токио и Нью-Йорка, включая сдвиг на другую дату.
- Идущий матч (m4): «Идёт, 67′» и счёт 1 : 1.
- Порядок матчей — как у сервера: сортировка по дате не вводилась, `null` в дате её бы осложнил.
- Длинные названия («Пари Нижний Новгород») переносятся на вторую строку.
- Битая запись (нет `id` или названия команды) пропускается с предупреждением в консоли, остальные остаются; ответ без массива `matches` — это ошибка с кнопкой «Повторить».

**Прочее.**

- В `MATCHES_URL` стояла заглушка `OWNER/REPO`, и запрос возвращал 404, хотя в комментарии написано «адрес менять не нужно». Подставлен адрес этого репозитория.
- Если обновление не удалось, прежний список остаётся на экране, сверху баннер с «Повторить», а «Обновлено N сек назад» считается от последней успешной загрузки.
- GitHub кэширует raw-файл на 5 минут (`Cache-Control: max-age=300`), поэтому «Обновить» сразу после правки `data/matches.json` может показать старые данные. Это не ошибка приложения.

## Баги из части 2

Сначала компоненты были подключены как есть, и обе жалобы воспроизведены (это видно по коммитам с пометкой «известная проблема»), затем исправлены отдельным коммитом.

1. Звёздочки: наличие проверялось через `Boolean(favorites.indexOf(id))`, а `indexOf` возвращает позицию: для отсутствующего элемента это -1 (`true`), поэтому горели все звёзды, а для первого — 0 (`false`), поэтому первая добавленная выглядела погасшей. Кроме того, `toggle` менял массив прямо в состоянии (`push`/`splice`) и передавал в `setFavorites` ту же ссылку: React сравнивает состояние по ссылке, не видел изменения и не перерисовывал экран, поэтому нажатие «не срабатывало», а результат проступал при случайной перерисовке (например, при смене фильтра). Исправлено: `includes` и новый массив через функциональное обновление `setFavorites`.
2. «Обновлено N сек назад»: `useEffect` с пустым списком зависимостей выполняется один раз, и функция внутри `setInterval` запоминает `seconds` из первого рендера (0): каждую секунду она записывает 0 + 1, поэтому подпись застывает на «1 сек», хотя таймер идёт. Проп `since` не использовался вообще, поэтому после «Обновить» подпись нечем было сбрасывать (счёт шёл от появления компонента, а не от загрузки данных), а таймер ещё и не очищался. Исправлено: в состоянии хранится текущее время, секунды считаются от `since`, эффект зависит от `since` и очищает интервал через `clearInterval`.

## Как я использовал ИИ

**Инструмент:** Claude Code в VS Code (модель Claude Sonnet 5.5). Работа шла по плану из пяти шагов; код писал агент, каждый шаг принимался отдельно, коммиты делались вручную после просмотра правок.

**Как проверялся результат:** перед каждым шагом `tsc --noEmit` и `npm test`; тесты проверены «на прочность» (код намеренно ломали, и нужные тесты падали); экран прогонялся в настоящем Chrome скриптами на Playwright (в репозиторий они не входят): данные, фильтры, часовые пояса, ошибки, пустые состояния, обновление; для обеих жалоб из части 2 — сценарий «до» (баг воспроизводится) и «после». Слой данных разобран с агентом построчно, приложение запускалось вручную через `npm run web`.

**Где ИИ ошибся или был неполон:**

1. Для вкладок фильтра был использован `accessibilityState={{ selected }}`, как в документации RN, но react-native-web 0.21 его игнорирует: в DOM не было `aria-selected`. Заметили проверкой в браузере; заменено на `aria-selected`.
2. Команда установки Jest из документации Expo (`npx expo install jest-expo jest @types/jest "--" --dev`) на npm 11 положила пакеты в `dependencies`. Заметили по `git diff` файла `package.json`; перенесены в `devDependencies`.
3. В плане предполагалось, что без `extraData` у `FlatList` звёзды могут не обновиться. Эксперимент (убрали `extraData` и прогнали сценарий в браузере) этого не подтвердил: в нашем коде всё работает и без него. `extraData` оставлен как страховка по документации, причиной бага он не назван.
